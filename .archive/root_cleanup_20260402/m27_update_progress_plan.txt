## 1. Why the Previous Patch Idea Was Unsafe

**Updating `StudentAbility`/`theta` from `update_progress`** would create a **second mastery write path** outside the quiz event pipeline. Daily truth source is `StudentAbility/theta` (via `submit_quiz ÔåÆ LearningEventService`). If `update_progress` also writes to `StudentAbility`, two writers race on the same rows ÔÇö BKT state diverges and the daily truth source invariant breaks.

**Converting `completed=True` into a synthetic correct answer** injects false signal into the mastery pipeline. A topic marked "completed" in the UI is not equivalent to a quiz being answered correctly. This corrupts theta estimates.

**Writing to `cat_sessions`** would corrupt adaptive testing state because CAT sessions are managed entirely by the assessment engine, not the progress endpoint.

**Using a fallback `subject_slug`** when none is provided silently defaults to a wildcard match, causing cross-subject contamination in mastery records.

## 2. Exact Contract for `update_progress`

```
Contract: INTERACTION STATE WRITE ONLY

Scope:
  - Persist {progress%, completed, time_spent} to TopicProgress
  - Persist {completed} to TopicCompletion (when completed=True)
  - NO writes to: StudentAbility, theta, BKT state, cat_sessions, mastery tables

Guarantees:
  - progress/completed = UI interaction signals, NOT mastery estimates
  - Actual mastery lives in StudentAbility/theta (written only by submit_quiz pipeline)
  - completion/completion_date in TopicCompletion are UI convenience fields
  - Re-calling with identical values is idempotent (upsert behavior)

Inputs consumed:
  - student_id, node_id (URL path)
  - ProgressUpdate {progress: 0-100, completed: bool, time_spent: int|null}
```
